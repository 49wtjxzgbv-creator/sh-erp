## Що це за проєкт

**SH ERP** (внутрішня назва файлів — SHSklad) — повноцінна система управління складом і виробництвом на **Google Apps Script + Google Sheets + Google Drive**. Не окремий сервер — увесь бекенд це `.gs`-файли Apps Script, база даних — Google Таблиця, файли (фото, PDF) — Google Диск.

**Мова інтерфейсу:** українська, для власника бізнесу (виробництво + продаж), не програміста.

**Технічний рівень власника:** вміє користуватись Apps Script (Deploy, Run, Script Properties), але не пише код сам. Спілкується неформально, зі скороченнями, часто присилає скриншоти/фото екрана з помилками.

---

## Архітектура

- **Сервер:** окремі `.gs`-файли за доменом (Products.gs, Assemblies.gs, CustomerOrders.gs, PurchaseOrders.gs, ProductionOrders.gs, Suppliers.gs, Gemini.gs, AI_FullAssistant.gs, Automation.gs, Employees.gs, Payroll.gs, тощо)
- **Клієнт:** один великий `JavaScript.html` (весь фронтенд-код), окремі `.html`-партіали для кожної сторінки/модалки (products.html, assemblies.html, customer-orders.html, purchases.html, settings.html і т.д.), спільний `Style.html`
- **API:** `Code.gs` містить `API_WHITELIST_` — об'єкт usіх функцій, які можна викликати з клієнта через `doPost`. **Кожна нова серверна функція, яку клієнт має викликати, ОБОВ'ЯЗКОВО додається сюди.**
- **База даних:** `Setup.gs` — схема всіх аркушів (`ensureSheet_` для створення, `ensureColumnsExist_` для міграції існуючих інсталяцій, `SCHEMA_VERSION_` — підвищувати щоразу, коли міняєш схему)
- **Аутентифікація:** `Auth.gs`, сесії через `CacheService`, ролі: `admin`, `storekeeper` (комірник), `viewer` (перегляд)

## Ключові збудовані підсистеми (хронологічно)

1. Базовий склад: товари, прихід/списання, віртуальні склади, історія
2. Вироби (специфікації/BOM) з версіюванням, включно з **багаторівневими виробами** (виріб зі виробів)
3. Виробничі замовлення: резервування → запуск (списання, серійні номери) → етапи виробництва → статуси `planned` → `in_progress` → `completed`
4. Контроль якості, відвантаження, інвентаризація
5. Замовлення клієнтів, з **поетапним виробництвом по кожному виробу окремо**
6. **Постачальники** (окрема сутність) + автоформування заявок постачальникам зі замовлення клієнта (розбивка по постачальниках, включно з рекурсивною перевіркою вглиб по вкладених виробах)
7. Друк: аркуш видачі, специфікація виробу, замовлення клієнта, заявки постачальникам — усе з чекбоксами "що включати" (фото/ціни/креслення) і спільним логотипом на всіх документах
8. Власне брендування — admin може завантажити свій логотип/емблему/фавікон через Налаштування
9. **Gemini AI інтеграція** — повноцінний асистент через function calling (не просто текстовий чат): читає реальні дані системи, генерує Excel/PDF, розпізнає накладні й довільні документи, прогнозує закупівлі, знаходить причини простоїв, голосовий режим (розпізнавання + синтез мовлення українською), підтвердження критичних дій перед виконанням

## КРИТИЧНО ВАЖЛИВІ конвенції — не пропускай жодну

### 1. Завжди віддавай ВЕСЬ архів, ніколи окремі файли
Навіть якщо змінив один файл — перепаковуй і віддавай повний zip. Власник завжди замінює все розгортання цілком.

### 2. Після КОЖНОЇ зміни коду — обов'язковий набір перевірок (bash)
```
- Синтаксис усіх .gs файлів: node -e "new Function(fs.readFileSync(f))"
- Дублікати оголошень функцій
- Баланс фігурних дужок по кожній функції окремо (див. пункт про "обезголовлені функції" нижче)
- Усі функції з API_WHITELIST_ реально оголошені десь у .gs файлах
- Усі виклики call('...') з клієнта є в API_WHITELIST_
- Синтаксис витягнутого <script> з JavaScript.html через node -c
- Усі getElementById(...) в JS мають відповідний id= в якомусь .html
- Немає дублікатів id= між html-файлами
- Відповідність кількості значень у appendRow([...]) кількості колонок у схемі аркуша (Setup.gs)
```
Це рутина, яку треба проганяти щоразу, не тільки "коли здається, що щось могло зламатись".

### 3. НАЙЧАСТІША реальна помилка, яку я (Claude) сам собі створюю
Коли вставляю НОВУ функцію ПЕРЕД існуючою через `str_replace`, дуже легко випадково "з'їсти" рядок оголошення (`function existingName(...) {`) чи закриваючу дужку `}` попередньої функції. Це давало синтаксичні помилки **щонайменше 4 рази** за час розробки. **Завжди після вставки нової функції — перевіряй баланс дужок ОКРЕМО по КОЖНІЙ функції у зміненому файлі**, не тільки загальний синтаксис файлу (загальний синтаксис може випадково "зійтись" навіть коли одна функція втратила межу, а сусідня її "поглинула").

### 4. Схема бази даних
- Кожна зміна схеми (нова колонка/аркуш) → підняти `SCHEMA_VERSION_` у Setup.gs, інакше `ensureDatabase_()` не запустить міграцію для вже існуючих інсталяцій
- Кожен новий аркуш: додати і в `ensureSheet_(...)` (створення з нуля), і в окремий `ensureColumnsExist_(...)` (міграція існуючих)
- Кожен `appendRow([...])` має ТОЧНО стільки значень, скільки колонок у схемі цього аркуша — рахувати вручну після будь-якої зміни схеми

### 5. Нагадай про розгортання
Після кожного архіву нагадай: замінити всі файли в Apps Script editor → `setupDatabase` вручну (якщо була зміна схеми) → **Deploy → Manage deployments → Edit → New version** (без цього кроку зміни не потрапляють на живий сайт — це вже траплялось і викликало плутанину).

### 6. Мій інструмент перегляду зображень часто НЕ ПРАЦЮЄ (повертає порожньо)
Якщо це станеться — НЕ вигадуй, що "бачив" результат. Або: (а) чесно скажи власнику, що не можеш перевірити візуально, і попроси його скриншот; (б) якщо є `wkhtmltoimage` в bash-оточенні — можна відрендерити HTML/CSS і перевірити **програмно** (кількість унікальних кольорів, bounding box конкретних елементів, піксельні виміри) замість "візуального огляду".

### 7. Google Gemini API — назви моделей змінюються ДУЖЕ часто
Використовуй псевдонім `gemini-flash-latest` (не конкретну версію типу `gemini-2.5-flash`) у викликах `generativelanguage.googleapis.com` — конкретні версії кілька разів "вмирали" для нових ключів за час розробки. Якщо власник знову присилає помилку квоти/недоступності моделі — шукай актуальну інформацію (web-пошук), не покладайся на пам'ять.

### 8. Автоматичні "розумні" обчислення складу — будь обережним
Була реальна помилка: логіка автоматичного віднімання залишків/резервів при формуванні заявок постачальникам порахувала неправильно, коли кілька виробів ділили спільний компонент. За проханням власника **спрощено навмисно**: тепер система показує повну потрібну кількість + поточний залишок ОКРЕМО, людина сама коригує — без прихованої арифметики. Тримайся цього принципу надалі: коли є вибір між "розумним" автоматичним розрахунком і прозорим показом сирих чисел з ручним контролем — власник явно віддає перевагу другому після цього досвіду.

## Стиль спілкування, який усталився

- Власник пише коротко, іноді з помилками, часто imperative ("Роби", "Продовжуй")
- Коли просить забагато одразу — чесно кажи, що встиг, а що ні, не вдавай, що зробив усе
- Даю оцінку "заміняйте весь архів" щоразу
- Емодзі-заголовки в підсумках (✅ ⏳ 🔧) — усталений формат відповідей, який власнику зручно сканувати
- Якщо власник надсилає фото помилки з екрана — уважно читай текст помилки, це майже завжди дає точну підказку (напр. "Cannot read properties of null (reading 'getDataRange')" = аркуш не існує)
