# ADR-0012: `SupplierOrganization` + `SupplierConnection` — one supplier login, many manufacturers

**Status**: Accepted (2026-08-21)

## Context

ADR-0011 explicitly left this as an accepted limitation, with a named revisit condition: *"a real-world supplier company that does business with two different SH ERP tenant companies cannot use the identical email for both portal accounts... revisit if this actually becomes a real complaint."* That complaint arrived: a real supplier works with several manufacturers on this platform and was forced into a separate account/password per manufacturer, with no way to log in once and switch.

The hard coupling lived in two places: `Supplier.companyId` (required — a `Supplier` row belongs to exactly one company, which is correct and unchanged by this ADR) and `SupplierPortalUser.supplierId` (`@unique` — exactly one portal account per `Supplier` row, which is what actually needed to change, since it meant one account per company by construction).

## Decision

Introduce a `SupplierOrganization` (a global, company-agnostic supplier identity, same "no RLS, `BYPASSRLS`-only" shape as `SuperAdmin`) and a `SupplierConnection` (the link between one `SupplierOrganization` and one company's `Supplier` row), replacing `SupplierPortalUser`'s direct 1:1 tie to a single `Supplier`/`Company`.

**Schema**: `SupplierPortalUser` moves from `{ supplierId @unique, companyId }` to `{ supplierOrganizationId @unique, lastActiveConnectionId }` — still exactly one portal account per organization, no RLS (global table, like `super_admins`). `SupplierConnection` reuses the existing `ImportConnection`/`ImportConnectionStatus` shape already in this codebase (`PENDING/PAIRED/REVOKED`, renamed here to `PENDING/ACTIVE/REVOKED`) rather than inventing a new state machine: `{ companyId, supplierId @unique, supplierOrganizationId, status }`, RLS-scoped on `companyId` exactly like `supplier_portal_users` was before (company staff manage it through the normal `app_user` path). `Supplier`/`ProductSupplier`/`AssemblySupplier`/`PurchaseOrder`/`PurchaseOrderItem` are **untouched** — they were already correctly anchored to `(companyId, supplierId)`, which remains the right anchor for "how this company recorded this supplier."

**Authorization — never trust the JWT for `companyId`/`supplierId`.** The access token now carries only `{ supplierOrganizationId, activeConnectionId }`. `SupplierPortalGuard` verifies the signature and stops there. `SupplierPortalScopeInterceptor` — on **every single request** — looks up the live `SupplierConnection` row for `activeConnectionId` through the existing `BYPASSRLS` `supplier_portal_auth_service` client, and only then derives real `companyId`/`supplierId` for the RLS transaction. A request is rejected (as a 404, matching `SupplierPortalService#getPurchaseOrder`'s existing "never distinguish not-yours from doesn't-exist" convention) if the connection doesn't belong to the token's own organization, isn't `ACTIVE`, or the account itself is deactivated. This was the explicit, non-negotiable requirement driving this design: a company revoking a connection must take effect on the *very next request*, not at the token's next natural expiry — a signed claim is only ever as fresh as the token's TTL, so the check has to happen against a live row, every time, not just when a "switch company" action runs.

**Switching companies**: a new `POST /supplier-portal/auth/switch-connection` re-verifies the target connection belongs to the caller's own organization and is `ACTIVE`, then mints a new access+refresh pair (same rotation family) with a different `activeConnectionId`. A plain `/refresh` carries `activeConnectionId` forward **unchanged** — the exact same "propagate unchanged through rotation" pattern already used for `RefreshToken.impersonatedBy` in `identity/auth.service.ts`. Only `/switch-connection` is allowed to change it. `SupplierPortalRefreshTokenService#peek()` validates a token without consuming it, so a *rejected* switch attempt doesn't burn the caller's still-valid session.

**Invitation flow** (`SuppliersService.invitePortal`, `procurement/suppliers.service.ts`): if the invited email already belongs to a *different* company's connected `SupplierOrganization`, no new account is created — a `PENDING` `SupplierConnection` is created instead, and the response carries `requiresAcceptance: true` (no `tempPassword`). The supplier accepts or declines it from their own portal (`GET/POST supplier-portal/connections`, `.../accept`, `.../decline`), guarded by `SupplierPortalGuard` alone — deliberately **not** wrapped in `SupplierPortalScopeInterceptor`, since listing/resolving connections is inherently cross-company and has no single-company RLS transaction to open. If the email is genuinely new, today's flow (temp password, argon2, email) is unchanged, just wrapped in a new organization + one `ACTIVE` connection instead of a bare `SupplierPortalUser`.

**A real bug fixed, not a preserved behavior**: `SuppliersService.deactivatePortal` previously set `SupplierPortalUser.active = false` — under the old 1:1 model that was correct, but under this model it would have let one company's deactivation silently lock a supplier out of *every* other company it's connected to. It now revokes only that company's own `SupplierConnection.status`, never the global account flag.

**Migration**: one forward migration, idempotent backfill (`WHERE "supplierOrganizationId" IS NULL` guard) — every existing `Supplier` with a portal account gets exactly one new `SupplierOrganization` and one `ACTIVE` `SupplierConnection` carrying its existing `(companyId, supplierId)`. **No new `Supplier` rows, no new `SupplierPortalUser` rows for existing accounts** — only new `SupplierConnection` rows are created during backfill. The old `companyId`/`supplierId` columns on `supplier_portal_users`/`supplier_portal_refresh_tokens` are dropped in the same migration that ships the new backend code (a hard cutover — see Consequences).

**Frontend**: the existing 3-page Supplier Portal (orders list, order detail, login) is unchanged. A company selector is added to the header, **hidden entirely** when the organization has exactly one `ACTIVE` connection and zero `PENDING` ones (the common case today), so the portal stays visually identical for the vast majority of suppliers. Switching does a full page navigation rather than a client-side store update, so no page can show stale data from the previous company.

`supplier_portal_auth_service`'s grants expand from 2 tables to 4: `+supplier_connections` (`SELECT, UPDATE`), `+supplier_organizations` (`SELECT`) — proportional to the interceptor now needing a pre-tenant-context lookup on every request, the same class of problem login already had.

## Consequences

- Positive: closes the exact gap ADR-0011 named as its own revisit condition — one supplier login now works across every manufacturer it's connected to.
- Positive: the "don't trust the JWT" design closes a real, related gap that existed even before this change — account deactivation was previously only checked at `/refresh`, not per request; it's now checked on every request as a side effect of the same interceptor lookup.
- Negative: `supplier_portal_auth_service`'s `BYPASSRLS` footprint doubles (2 → 4 tables) — mitigated the same way ADR-0009/0010/0011 mitigate this: each grant is narrow (one table, one or two verbs) and reviewable in a sentence.
- Negative: a per-request `SupplierConnection` lookup adds one PK-indexed read to every Supplier Portal request — proportional to (and smaller than) the two lookups `TenantScopeInterceptor` already pays for every regular tenant request (`Company.status`, `User.active`).
- Negative: the migration's column-drop steps are a hard cutover — this migration and the corresponding backend code **must** ship in the same release, with a short technical window for the Supplier Portal specifically (not the whole app) during deploy. Internal company-staff users are entirely unaffected.
- Deliberately deferred: connection list entries don't show a purchase-order count per company (the illustrative "12 заявок" in the original request) — adding that would mean granting `supplier_portal_auth_service` a fifth table (`purchase_orders`) purely for a display nicety on the selector. The real order list is one click away after switching; revisit if this becomes an actual ask.

## Alternatives considered

- **Keep `companyId`/`supplierId` in the JWT, re-validate only at `/switch-connection`**: rejected — doesn't close the actual complaint driving this ADR ("a company revoked access mid-session, but the token is still valid for up to 30 minutes"). The whole point of the per-request interceptor lookup is that a signed claim is only as fresh as the token's TTL, independent of how carefully a switch endpoint validates.
- **A 4-state connection enum** (something like `PENDING/ACTIVE/SUSPENDED/REVOKED`): rejected in favor of reusing the existing 3-state `ImportConnection` pattern already proven in this codebase — no evidence a 4th state is needed yet, and `revokedAt`/`AuditEvent.action` already capture "why" without a new enum value.
- **A brand-new Supplier Portal / redesign**: explicitly out of scope per the request — this ADR is additive to the existing 3-endpoint portal, not a rebuild.
