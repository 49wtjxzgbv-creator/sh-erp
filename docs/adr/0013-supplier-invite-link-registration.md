# ADR-0013: Self-service supplier registration via a single-use invite link

**Status**: Accepted (2026-08-21)

## Context

ADR-0012 let one `SupplierOrganization` connect to many companies, but the only onboarding path (`SuppliersService.invitePortal()`) still requires company staff to already know the supplier's exact portal email up front. The owner asked for a self-service alternative: staff generate a shareable link/code for a `Supplier` row that has no portal connection yet, hand it to the supplier out-of-band (email/phone/messenger — never in-app discovery or a public directory), and the supplier redeems it themselves — either registering a brand-new account or, if they already have one from a different company, proving ownership of it with their existing password.

This is explicitly **not** a marketplace/cold-outreach feature: the invite token is always generated from an existing `Supplier` row staff already created in their own ERP. There is no public catalogue and none is planned here.

## Decision

**`SupplierInviteToken`** — one row per outstanding invite, same hash-at-rest shape as `SupplierPortalRefreshToken` (`randomUUID()+randomUUID()` raw token, sha256 hex `tokenHash`), plus `consumedAt` (single-use) and a separate `revokedAt` (manual invalidation — kept apart from `consumedAt` so an audit trail can tell "someone redeemed it" from "staff invalidated it / superseded it with a new one"). RLS-scoped on `companyId` exactly like `supplier_connections` — staff generate/list/revoke tokens through the normal `app_user` path (`POST/GET suppliers/:id/invite-links`, `POST suppliers/:id/invite-links/:linkId/revoke`). Generating a new link automatically revokes any previously outstanding one for that supplier, so at most one is ever live.

**Public redemption** (new `supplier-portal-registration.controller.ts`, `@Public()`, no `SupplierPortalGuard` — there is no token to verify yet, the invite token itself is the gate): `GET supplier-portal/auth/invite/:token` previews `{companyName, supplierName}` for the registration page; `POST .../accept` redeems it. If the submitted `email` already has a `SupplierPortalUser`, a correct `password` is the proof of ownership — replacing the separate accept/decline step `invitePortal`'s own case 2 defers to, since nobody is vouching for this supplier here — and attaches a new `ACTIVE SupplierConnection` immediately (no PENDING step; the password check already is the authorization). If the email is new, `organizationName` is required and a full `SupplierOrganization`+`SupplierPortalUser`+`ACTIVE SupplierConnection` are created together. Both branches return a full session (auto-login), reusing the exact same `reissueAccessToken` re-verification every other session-minting path in the module already gets, via a new `SupplierPortalAuthService.issueSession()`.

**First-ever INSERT grant to `supplier_portal_auth_service`.** Every previous expansion of this BYPASSRLS role (ADR-0011, ADR-0012) was SELECT/UPDATE on *existing* rows for a pre-tenant-context *lookup* — ADR-0011 stated plainly that account creation "happens through the normal app_user path... a different code path than login" as a deliberate property, not an oversight. Self-service registration breaks that property by necessity: it is structurally pre-tenant-context, so there is no `app_user` path available at all for this one action. New grants: `SELECT, UPDATE` on `supplier_invite_tokens`; `SELECT` on `suppliers` (previously none); `INSERT` on `supplier_organizations`, `supplier_portal_users`, `supplier_connections` (previously SELECT/SELECT+UPDATE/SELECT+UPDATE respectively, no INSERT on any). **The compensating control is not that this grant is narrow — INSERT is INSERT.** It's that the only code path that ever exercises it first validates a single-use, unexpired, unrevoked `supplier_invite_tokens` row scoped to exactly one `(companyId, supplierId)` pair — the same "the endpoint itself is the authorization boundary, not RLS" reasoning already accepted in this codebase for `POST /companies/signup` (`CompanyService.createCompany()`).

**Atomicity.** The accept flow does several creates that must not partially succeed: wrapped in `SupplierPortalAuthPrismaService.$transaction(...)`. Token consumption is a conditional `updateMany({ where: { id, consumedAt: null, revokedAt: null, expiresAt: { gt: now } }, data: { consumedAt: now } })` checked for `count === 1` — not read-then-write — so two concurrent redemptions of the same token can never both proceed; `SupplierConnection.supplierId`'s existing `@unique` constraint is a second, independent backstop against the same race.

**Audit trail.** Every other identity-mutating action in this module runs through an authenticated `RequestUser` and is already audited; self-service accept is the one exception (`actorUserId: null`), so both branches call `AuditService.record()` explicitly (`supplier.connected_via_invite_link` / `supplier.registered_via_invite_link`). The existing-account branch also emails the account's own registered address ("a new company was just connected to your account") — a cheap tripwire against a leaked-link-plus-guessed-password takeover.

**Throttling.** First `@Throttle()` usage anywhere in this codebase — the global `100/60s` per-IP baseline (`app.module.ts`) was never tightened per-route, not even for login. `GET .../invite/:token`: 20/min/IP. `POST .../accept`: 5/min/IP. **The throttle is not the real backstop** — a link forwarded over email/messenger isn't bound to one IP — the invite token's short TTL (`SUPPLIER_INVITE_LINK_TTL_DAYS`, default 14) and single-use consumption are what actually bound the exposure window; the throttle is defense in depth against straightforward brute-forcing, not the primary control.

## Consequences

- Positive: closes the "staff must already know the exact portal email" gap without requiring a public directory or any new discovery surface.
- Positive: reuses every existing pattern in the module (hash-at-rest tokens, "never distinguish invalid from expired from consumed", `reissueAccessToken`'s re-verification, the `invitePortal`-style 2-branch split) rather than inventing new ones.
- Negative, accepted: `supplier_portal_auth_service` can now create real identity rows outright, not just read/update existing ones — a compromised credential for this role is meaningfully worse than it was before this ADR. Mitigated by the token being the sole practical gate on that capability, not by the grant being narrow.
- Negative, accepted: per-route throttling values (20/min, 5/min) have no prior art in this codebase to validate against; revisit if real abuse patterns emerge.
- Deliberately out of scope: no public catalogue/marketplace, no "cold" supplier self-registration without a staff-generated token, no CAPTCHA (none exists anywhere in this codebase; introducing one was judged disproportionate to a B2B invite-link flow).

## Alternatives considered

- **A separate, narrower BYPASSRLS role scoped only to invite redemption**: rejected — doesn't reduce risk (same database, same INSERT capability, just a second credential to provision/rotate/monitor per ADR-0009's own cost framing), and breaks this codebase's "one role per problem class" convention (`supplier_portal_auth_service` already handles several pre-tenant-context problems: login, refresh, scope-check).
- **A PENDING intermediate step for the existing-account branch** (mirroring `invitePortal`'s case 2, requiring a separate accept click): rejected — password verification already IS the proof-of-ownership step that case 2 defers to a later click; adding a second confirmation step would be redundant, not safer, and would defeat the self-service/auto-login goal. The real gap this raised (staff have no visibility into a self-service connection until after the fact) is closed via the audit event + notification email instead of a blocking approval step.
- **Creating a new `Supplier` row during registration** rather than requiring one to pre-exist: rejected — `SupplierConnection.supplierId` is `@unique` and `Supplier` already carries contact/notes/PO-history that predates any portal relationship; inventing a fresh row at registration time would orphan it from that bookkeeping.
