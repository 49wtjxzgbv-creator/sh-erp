# SH ERP API — backend

NestJS backend for SH ERP v2. Phase 5 implementation, built module by module per the roadmap in "SH ERP v2 — Phase 2 Architecture.md" §26.

## Modules shipped so far

- **Module 1 — Tenancy, Identity, Authorization**: company signup (`POST /api/v1/companies/signup`), login/refresh/logout (ADR-0006 rotating refresh tokens + reuse detection, transparent legacy-SHA-256→argon2id re-hash), RBAC (fixed permission catalogue, per-company roles, `@RequirePermissions()`). **User/role/audit management (added during production-readiness pass, closes the gap item 5 used to list here)**: `UsersModule` (`GET /users`, `POST /users/invite` — creates a brand-new global `User` + temp password for a new email, or attaches an existing global `User` via a new `CompanyMembership` for one that already has an account elsewhere, mirroring the schema's designed-in multi-company-per-user support; `PATCH /users/:userId/role`; `POST /users/:userId/deactivate` — deletes the `CompanyMembership` row only, never the global `User`, blocks self-removal and blocks emptying a company's last membership; `PATCH /users/me/password`), `RolesController` added to the existing `RolesService` (`GET /roles`, `GET /roles/permissions-catalogue`, `POST /roles`, `PATCH /roles/:id`, `DELETE /roles/:id` — `isSystem` roles can have name/description/permissions edited per `schema.prisma`'s own field comment, but never deleted; delete also blocked while any `CompanyMembership` still references the role), all gated by the `users:invite`/`users:manage`/`roles:manage` permissions that were already in `PERMISSIONS_CATALOGUE` and granted to the seeded Admin role but had no implementing controller until now. Audit trail is read-only exposure of the existing `AuditModule` (`GET /audit-events`, `GET /audit-events/entity/:entityType/:entityId`, gated `audit:read`) — no new write path, every module already writes through `AuditService.record()`.
- **Module 2 — Audit + Files**: `AuditService.record()`/`query()` (global module, every other module logs through it), R2-backed presigned-upload file attachments scoped `tenants/{companyId}/{domain}/{entityType}/{entityId}/{filename}`.
- **Module 3 — Catalog + Settings**: `ProductsService` (CRUD + query/pagination), `CompanyUnitsService` (seeds 6 default units at signup, in-use guard on delete), `SettingsService` (company settings + branding upsert). **Excel bulk import/export (added during production-readiness pass, first of the 4 secondary features the owner explicitly prioritized)**: `ProductsImportExportService` (`src/modules/catalog/import-export/`) ports the legacy `ImportExport.gs`'s fuzzy multi-language header-matching (`FIELD_SYNONYMS`/`buildHeaderMap`, unchanged logic, now TypeScript) via `exceljs`. `POST /products/import` (multipart, `FileInterceptor` — a genuinely new file-transport pattern for this backend, see the service's own header comment for why it doesn't reuse the R2-presign flow) upserts by `article` (citext, case-insensitive), row-level errors collected not thrown (partial success, matching legacy), auto-creates an unrecognized `CompanyUnit` by name (Phase 3 decision 1 turned free-text `unit` into a required FK — this preserves the legacy "any text works" ergonomics), and posts any imported qty as a real `ADJUST` `StockService` movement rather than writing `Product.qty` directly (the atomic-ledger rule below applies to imports too). `GET /products/export` streams a real `.xlsx` — and, as a genuine gap fix rather than a straight port, blanks all 5 price columns unless the caller's role also has `reports:valuation` (`ProductsController`/`ProductsService` themselves have no such gate today — every `products:read` role including Viewer currently gets full pricing from the plain REST endpoints; only the AI `SearchProductsTool` had ported the legacy `user.role === 'admin'` price check before this). Product photo import/export (legacy's `_photoBase64`/`Фото URL`) is deliberately NOT ported — `Product` has no photo column in the new schema at all, photos are `FileAsset` attachments added after a product already exists, a different flow entirely (Task 43's `FileUploadField`). The `loadPermissionSet` helper this reuses moved from `modules/ai/ai-permissions.util.ts` to `common/authorization/permission-set.util.ts` since it was never AI-specific.
- **Module 4 — Inventory**: `WarehousesService` (seeds one default warehouse at signup, single-`isDefault` enforcement, nonzero-stock delete guard), `StockService` (atomic increment-based ledger — see "atomic stock ledger" note below), `InventorySessionsService` (stocktake snapshot → count → discrepancy-only reconciliation via `StockService.applyMovement`).
- **Module 5 — BOM**: `AssembliesService` — Assembly/BOM-line CRUD, immutable `AssemblyVersion` snapshot on every BOM save (with save-time cycle rejection, not the legacy's silent truncation — Phase 1 §10.5), recursive per-unit cost calculation (`calculateCost`, local + German), recursive component-requirement flattening + `checkAvailability`, and the reservation-free `produce()` path (`ASSEMBLY_CONSUMPTION` stock movements) — kept deliberately distinct from the full ProductionOrder lifecycle in Module 6 (Phase 1 §6.1).
- **Module 6 — Production + QC**: `ProductionOrdersService` (the full reserve→start lifecycle — locks in the assembly's current BOM version at creation, checks availability, physically consumes raw-material components AND FIFO-consumes already-manufactured sub-assembly `FinishedGood`s, freezes cost at start time, generates serialized `FinishedGood`s, splits piecework pay, enters stage tracking or completes immediately), `FinishedGoodsService` (serial generation via `pg_advisory_xact_lock`, the Postgres-native equivalent of the legacy `LockService` lock), `QcService` (records a check, flips a finished good between `IN_STOCK`/`REWORK`), `ProductionStagesService`/`QcChecklistService` (configurable lists, no defaults seeded). See `production-orders.service.ts`'s header comment for why sub-assembly consumption does NOT recursively re-expand the BOM — each `FinishedGood`'s frozen unit cost already carries that.
- **Module 7 — Procurement**: `SuppliersService` (simple CRUD, deliberately NO in-use-reference guard on delete — matches the legacy behavior exactly, safe because every reference to a supplier is `onDelete: SetNull`), `PurchaseOrdersService` (multi-line POs; `receive()` posts `RECEIVE` stock movements through `StockService` for lines with a linked product, tracks partial delivery via an atomic `qtyReceived` increment, records `actualPrice` separately from `expectedPrice`, and recomputes `ORDERED`/`PARTIAL`/`DELIVERED` from the full item set on every receiving call).
- **Module 8 — Sales**: `CustomerOrdersService` (order header + items, the staged/"poetapne" give-to-production workflow — one line or the whole order, repeatable into independent batches via `ProductionOrdersService.create`, each batch linking back via `ProductionOrder.customerOrderItemId`), `CustomerOrderShortageService` (the recursive shortage-collection engine, ported faithfully including its two sharpest edges: shared mutable pools across the *whole* order rather than per-line, so a component shared by two order lines isn't undercounted, and the explicit "no hidden arithmetic" rule — gross requirement and current stock/finished-goods count are always shown side by side, never netted automatically; see the service's own header comment for the full recursion rule around `defaultSupplierId`), `ShipmentsService` (groups `FinishedGood` serials into a shipment, flips them `SHIPPED`/back to `IN_STOCK` on delete).
- **Module 9 — HR**: `EmployeesService` (deactivate-only, never hard-deleted — the schema has no `deletedAt` for `Employee`, only an `EmployeeStatus` enum, matching the legacy behavior exactly), `PayrollService` (manual ADVANCE/BONUS/PENALTY entries only — PIECEWORK is system-generated exclusively from `ProductionOrdersService.start()` — with the sign convention applied automatically from a positive input magnitude; `getPayrollSummaryReport` cross-references QC `REWORK` results back through each employee's assigned production orders, with every list batched once up front rather than queried per employee, following the same discipline the legacy codebase itself had to learn the hard way for a similar reservation calculation).
- **Module 10 — Reports**: `ReportsService` (3 read-only aggregations ported from the legacy `Reports.gs`, Phase 1 §3.6): `getReorderSuggestions` (target = 2× `minQty`, `available = qty − reservations`, with reservations batched from PLANNED `ProductionOrder`s' locked BOM PRODUCT-lines — one level deep, matching exactly what `ProductionOrdersService.start()` consumes, not a recursive re-flattening; IN_PROGRESS/COMPLETED orders are excluded since they've already physically consumed their components), `getWarehouseValuation` (all 5 legacy price fields × qty, grouped by category + grand total — gated behind the new `reports:valuation` permission, admin-only per the legacy RBAC matrix, since it exposes cost/price data), `getMonthlyProductionRollup` (COMPLETED orders grouped by assembly over a date range, using each order's frozen `totalLocalCostEur`/`totalGermanCostEur`).
- **Module 11 — AI**: provider-abstracted (`AiProviderPort`/`GeminiAdapter`, Phase 2 §8) — nothing outside `providers/gemini.adapter.ts` knows Gemini specifically, model reference stays an alias (`AI_MODEL_ALIAS`, default `gemini-flash-latest`) never a pinned version, and the adapter preserves the legacy one-retry-on-429 behavior. `AiService` has three entry points ported from `Gemini.gs`/`AI_FullAssistant.gs` (Phase 1 §3.7): `askHelp` (instruction-only "Довідник", zero live-data access), `askAboutCustomerOrder` (narrowly-scoped Q&A over one order's real data), and `askFullAssistant` (the function-calling assistant, looping over `AiToolsRegistry`'s 16 tools — ported 1:1 from `AI_TOOLS_`/`executeAiTool_`, each tool reusing the relevant domain module's service rather than re-implementing its logic; see each tool file's header comment for which one). Critical actions (currently just `adjustProductStock`) never execute inline: `AiToolsRegistry.executeTool` always short-circuits a `critical` tool to a `needs_confirmation` response, `AiService` persists that as a durable `PendingAiAction` row (Phase 2 §8's replacement for the legacy in-memory/token-based confirmation — survives a page refresh or pod restart), and only `AiActionsService.confirmAction`, called from a separate explicit `POST /ai/confirm-action` after the user clicks confirm, ever runs the tool's real `execute()`. `AiSettingsService` manages a per-company bring-your-own API key (AES-256-GCM envelope encryption, `src/modules/ai/ai-crypto.util.ts` — see its header comment for the disclosed gap versus real KMS) and a monthly token quota (`AiActionsService.checkQuota`, `AiUsageLog` aggregate — see the same service's header comment for the disclosed gap versus Phase 2 §8's Redis-token-bucket rate limiting, not wired up in this codebase yet). `exportToExcel`/`exportToPdf` produce CSV/plain-text files instead of real `.xlsx`/`.pdf` (disclosed format substitution, no new binary-generation dependency pulled in) via a new `FilesService.uploadEphemeralExport` path that deliberately does NOT use the frozen `FileAsset`/`FileDomain` model — see that method's header comment for why.
- **Module 12 — Notifications + Billing stub**: `LowStockDigestService` (ported from `dailyLowStockDigest_`, Automation.gs) builds the same two-part digest — products below `minQty`, plus products forecast to run out within 14 days at their trailing 60-day consumption rate — and sends it via `EmailService` (a thin SMTP/`nodemailer` wrapper, `SMTP_*` env vars, fails open to a log line if unconfigured) to `CompanySettings.dailyDigestEmail` when `dailyDigestEnabled` (Module 3, already existed — no new settings needed). Telegram mirroring is NOT ported (deprioritized per Phase 0). Callable on demand (`POST /notifications/low-stock-digest/send-now`); **not** on an automatic daily schedule — see that service's header comment for exactly why (no BullMQ/Redis wired up yet, and a real cron job would need a cross-tenant read no current DB role is scoped for — flagged as an architecture decision, not silently built around). `BillingModule` (Phase 0 stub): `Plan`/`CompanySubscription` now actually seeded/used — `prisma/seed.ts` gained a `Plan` seed step (3 tiers: starter/growth/enterprise) alongside its existing `Permission` seeding, and `CompanyService.createCompany` now creates a `CompanySubscription` on the free `starter` plan for every new company via `BillingService.seedDefaultSubscription(tx, ...)`, threaded through the same signup transaction as every other per-company seeder. `GET/PUT /billing/subscription` (`company:billing`, already in the catalogue) let a company view/switch its plan — `updatePlan` is explicitly a stub: it records the change, it does not collect payment or call Stripe.

### Two-layer multi-tenant enforcement (ADR-0002) — now RLS-correct

`src/prisma/prisma-tenant.extension.ts` (app-layer, auto-injects/validates `companyId` on every tenant-scoped query) + `TenantScopeInterceptor` (`src/common/interceptors/tenant-scope.interceptor.ts`, DB-layer). The interceptor opens one Postgres transaction per request, issues `SET LOCAL app.current_company_id` inside it so RLS actually activates, does permission-checking in that same transaction, then runs the rest of the request inside it via `next.handle()`. This replaced an earlier `PermissionsGuard`-only design that never activated RLS at all — Nest runs Guards before Interceptors, so only an Interceptor can wrap `next.handle()` in a transaction. `PrismaService.tenant` reads the active transaction from `tenantTxStorage` (`src/prisma/tenant-tx-context.ts`, `AsyncLocalStorage`).

### `auth_service` DB role — APPROVED and implemented (ADR-0009)

Login, refresh, and pre-login company discovery must query RLS-scoped tables (`company_memberships`, `refresh_tokens`, `company_branding`) *before* a tenant is known — which strict RLS cannot do with the app's normal `app_user` role. `src/prisma/auth-prisma.service.ts` (`AuthPrismaService`, used only by `AuthService`, not exported from `IdentityModule` so nothing else can inject it) connects instead via a second, least-privileged role, `auth_service`, with narrow per-table `GRANT`s and `BYPASSRLS`. Full rationale in `docs/adr/0009-auth-service-bypassrls-role.md`; the raw `CREATE ROLE`/`GRANT` SQL is in `prisma/migrations/20260804000000_create_auth_service_role/migration.sql`; see "SH ERP v2 — Phase 3 Database Schema.md" §2c for how this fits the two-layer isolation model. This role must never be used once a tenant context has been resolved — every method that touches it is on an `@Public()` route.

**Related fix, found while implementing the above**: `CompanyService.createCompany` (company signup) had the identical class of bug — it wrote to FORCE-RLS tenant-scoped tables (`company_memberships`, and via the per-module seeders `roles`/`role_permissions`/`company_units`/`warehouses`) without ever activating a tenant transaction. Fixed by generating `companyId`/`userId` client-side and opening the transaction via the already-existing `PrismaService.runInTenantTransaction` — no new role needed, no schema change, just correct use of Phase 2 §11.4's mechanism.

## Standing requirement carried over from Phase 3/4

`prisma migrate dev` has never been run for real against this schema outside a static structural checker (sandbox network restriction during Phases 3-4 — see database-schema.md §8). **This should be the first thing done against this codebase**, before trusting anything else here — composite foreign keys, `citext`, explicit `onDelete` policies, and the `@@unique([companyId, legacyId])` constraints are all real Postgres/Prisma syntax that has only been approximated by a hand-written checker, never compiled by the actual engine.

## Atomic stock ledger pattern (Module 4)

`StockService.applyMovement` never reads current qty then writes it back — every mutation is a Prisma `{qty: {increment: delta}}` against `WarehouseStock`, with `StockMovement.qtyAfter` stamped from that same post-increment value, and `Product.qty` (denormalized total cache) updated with the identical increment in the same call. This avoids lost-update races under concurrent movements without needing row locks.

## Verification methodology note (discovered while building Modules 11-12)

The isolated `tsc --noEmit --skipLibCheck` check used to verify every module this phase turned out to have a blind spot worth recording: running `tsc` directly against `backend/`'s own `node_modules` silently produces **zero semantic diagnostics at all** (not even for a deliberately-broken import), even though it correctly reports syntax errors. Root-caused to that `node_modules` directory itself being in a partially-installed, corrupted state from an interrupted `npm install` (stray `.prisma-<hash>`/`.client-<hash>` temp directories left behind — this sandbox's mounted filesystem doesn't support the atomic renames `npm install` needs, so an install started in this environment can't safely finish; `npm install` truly must be run on a real filesystem, not this mount).

A clean scratch install (real `typescript` + every actual dependency at the project's pinned versions) fixed the blind spot and was used to re-verify Modules 11-12 by type: zero genuine errors, only the already-understood noise pattern (missing real Prisma-generated types — `prisma generate` is separately blocked in this sandbox by a 403 on `binaries.prisma.sh` — causing `TS2339`/downstream `TS7006` implicit-`any` on every Prisma-touching file in the whole codebase, old and new alike). One genuine bug WAS caught this way and fixed: `LowStockDigestService` had the same "`new Map(arr.map(p => [p.id, p]))` loses tuple inference" pitfall documented elsewhere in this codebase — fixed the same way, explicit `Map<string, any>` + a `for` loop.

Going further, a hand-written runtime stub for `.prisma/client/default` (a bare-bones `PrismaClient`/`Prisma.PrismaClientKnownRequestError` shape, good enough to satisfy imports but with no real query engine behind it) let the scratch install's copy of **every existing `.spec.ts` file in the whole repo actually execute**, not just type-check, for the first time this phase. Result: 198/201 tests passed. The 3 failures were investigated one by one:
- **`assemblies.service.spec.ts` (Module 5) — real bug, fixed.** `AssembliesService.calculateCost()` called `this.findOne(...)` (one `assembly.findUnique`) and then `calcAssemblyCostRecursive()` (which does its own, fully redundant, second `assembly.findUnique` for that same top-level id) — `calcAssemblyCostRecursive` already throws `NotFoundException` itself if the assembly doesn't exist, so the first call was pure waste. Against a real database both calls would've returned the same correct row, so this was silent (an unnecessary round trip, not a wrong answer) — but it happened to break under Jest's per-call `mockResolvedValueOnce` sequencing, which is exactly how the test caught it. Fixed by deleting the redundant `findOne()` call.
- **`inventory-sessions.service.spec.ts` (Module 4) — test-mock fidelity gap, fixed; source code was already correct.** The test's mock for `inventoryItem.findMany` returned a flat, unfiltered array regardless of the `where: { counted: true }` clause the real service passes — so an uncounted item that real Postgres would have excluded was fed back into the test as if it had matched, producing a spurious extra reconciliation movement. Fixed by making the mock actually honor the `where.counted` filter.
- **`products.service.spec.ts` + `company-units.service.spec.ts` (Module 3) — inconclusive, left alone.** Both failures are `instanceof Prisma.PrismaClientKnownRequestError` checks not matching against my hand-rolled stub class. The source code's pattern (`err instanceof Prisma.PrismaClientKnownRequestError`) is the textbook-correct way to detect a Prisma P2002/P2003 error and needs a *real* generated client to verify properly either way — this almost certainly a stub-fidelity artifact, not a real bug, but couldn't be fully confirmed in this sandbox.

**Bottom line for whoever runs this for real:** the very first thing to do outside this sandbox is a real `npm install` + `npm run prisma:generate` against an actual filesystem/network, then `npm test` for a genuinely complete check (type-check AND execution) — every module in this repo had, until this pass, only ever been checked with Prisma's generated types absent and its test suite never actually run.

### Deployment documentation pass — real gaps found and fixed, not just documented

Writing `docs/deployment.md` surfaced several genuinely load-bearing gaps that would have blocked or broken a real first deploy. Per this project's standing rule, all were fixed for real rather than left as caveats:

1. **No baseline SQL migration existed at all.** `prisma/migrations/` had only `20260804000000_create_auth_service_role` and `20260805000000_enable_rls_and_check_constraints` — both explicitly assume a fully-created schema neither one actually creates. Against a fresh database, `prisma migrate deploy` would have created nothing and both existing migrations would have failed immediately. Fixed by generating `prisma/migrations/20260803000000_init/migration.sql` (and the previously-missing `migration_lock.toml`) **programmatically from `schema.prisma`** — a small Python parser (not checked into the repo; a one-off verification tool) that walks every model/enum and emits `CREATE TYPE`/`CREATE TABLE`/index/FK statements, chosen specifically to avoid the transcription-omission risk of hand-typing ~48 `CREATE TABLE` statements (the same class of risk that produced gap #2 below in the first place).
2. **The RLS/CHECK migration referenced columns that don't exist.** `20260805000000_enable_rls_and_check_constraints` (written in the prior production-readiness pass) used snake_case columns (`company_id`, `product_id`, …), but `schema.prisma` has `@@map()` on every model (table names) and deliberately no `@map()` on individual fields — so Prisma's real generated columns are the exact camelCase field names, quoted (`"companyId"`, `"productId"`). As originally written, every statement in that file would have failed with "column does not exist." Rewritten to use the correct column names.
3. **No CORS configuration existed anywhere in this app**, despite `frontend/lib/api-client/http.ts` calling this API straight from the browser for every module except the 3 Next-owned auth routes. Fine by accident in same-origin/localhost testing, but every one of those calls would have been rejected by the browser once frontend (Vercel) and backend (Railway) are on different origins. Fixed via `app.enableCors(...)` in `main.ts`, driven by a new `FRONTEND_URL` env var (see `.env.example`).
4. **No `docker-compose.yml`, CI workflow, `railway.json`, or `vercel.json` existed anywhere in the repo** (confirmed via `find` before writing any of them), despite Phase 2 §17 calling for all four. Built real versions of all four — see `docs/deployment.md` for what each one deliberately does and does not cover (e.g. no Redis/worker service, since nothing in this backend consumes Redis yet; no separate `deploy-staging.yml`/`deploy-production.yml`, since today's deploy path is each provider's native Git integration gated by `ci.yml`).
